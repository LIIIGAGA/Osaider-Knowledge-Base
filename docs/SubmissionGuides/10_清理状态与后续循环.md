# 第 10 部分：清理状态与后续循环

## 本部分目标

确保第一轮鉴定结束后，玩家可以继续探索并再次按 D 打开 Submission，而不会出现：

- 旧槽位图标残留；
- `bCheckInProgress` 永远为 True；
- 旧 Pending Module 被再次 Reveal；
- 第二个 Submission Widget；
- 后续每次仍重复第一次教学；
- 已显示模块再次被选中。

## 1. 确认一次鉴定完成后的数据状态

Commit 成功后应满足：

- `PendingRevealModule == None`；
- `bCheckInProgress == False`；
- 新模块已经加入 `SpawnedModules`；
- `SubmittedItems` 按旧规则清空；
- `IdeologySum` 重置；
- Widget 已关闭；
- PlayerController `bUIInteractionLocked == False`；
- CoreDevice `SubmissionTutorialState == Completed`。

在 `CommitPendingReveal` 末尾临时 Print 这些值。

## 2. 创建统一的 CoreDevice 清理函数

如果旧项目没有集中清理函数，创建：

`ResetTemporarySubmissionState`

这个函数只处理临时 Submission 数据：

```text
清空/重置 SubmittedItems 三个槽位
→ IdeologySum = 0
→ 临时 Roll/FinalScore 按需求重置
→ PendingRevealModule = None
→ PendingFactionTag = None
```

不要在这里清空：

- `SpawnedModules`；
- `TriggeredInitialModules`；
- `SubmissionTutorialState`；
- 永久 Inventory（除非旧规则确实会消耗上缴物品）。

## 3. 决定物品是否消耗

必须检查旧 `BeginCheck` 的实际行为。

### 如果旧系统会消耗上缴物品

Commit 成功后：

1. 从 Inventory 移除三个对应物品。
2. 刷新 Inventory UI。
3. 清空 `SubmittedItems`。
4. `RefreshSubmissionAvailability`。

此时玩家需要重新获得三个物品才会再次可用。

### 如果旧系统不消耗物品

Commit 成功后：

1. 只清空 `SubmittedItems`。
2. Inventory 保留。
3. 根据设计决定是否立刻再次可用。

如果不希望玩家无限重复使用同一批物品，需要另建 Used/Consumed 规则；不要在本次 UI 改造中无意改变它。

## 4. Widget 关闭前清理视觉

如果 Widget 每次 Remove 并重建，视觉会自然重置，但仍建议创建：

`ResetSubmissionPanelVisuals`

节点：

```text
Set Image_Item0/1/2 Visibility = Hidden
→ Clear Brush（可选）
→ Set Button_Check Disabled
→ Set Image_OuterRing Angle = 0
→ Set Canvas_Root Render Opacity = 1
→ Set ActiveSlotIndex = -1
→ Set SubmissionState = Closed
```

如果复用同一个 Widget，这个函数是必需的。

## 5. PlayerController 单实例处理

### Remove 方案

`CloseSubmissionPanel`：

```text
SubmissionPanelRef.RemoveFromParent
→ Set SubmissionPanelRef = None
```

下次按 D 再 Create。

### 复用方案

```text
Set Visibility Collapsed
```

下次打开：

```text
Set Visibility Visible
→ InitializeSubmissionPanel
```

第一版推荐 Remove 方案，逻辑更直观。

## 6. 后续两个入口都直接打开

新方案中，第一次不是“必须点击右上角红色入口”才能完成教学。玩家第一次通过任意入口成功打开面板时，`OpenSubmissionPanel` 都已经设置：

`CoreDevice.SubmissionTutorialState = Completed`

两个入口始终并列：

```text
IA_OpenSubmission Started（D 键）
→ HandleOpenSubmissionInput
→ CanOpenSubmission
→ OpenSubmissionPanel

Button_SubmissionLauncher.OnClicked（右上角红色图标）
→ HandleOpenSubmissionInput
→ CanOpenSubmission
→ OpenSubmissionPanel
```

后续循环中：

- D 键仍然直接打开面板；
- 右上角红色图标仍然直接打开面板；
- 两者都不会显示首次教学 Attention；
- 两者都不会执行 `PrepareDiceCheck`；
- 只有面板中央 `Button_Check` 执行鉴定。

不要在 PlayerController、HUD 或临时 Widget 中另外维护一个教学完成 Boolean，也不要再次设置 `PointingToLauncher`。

## 7. 后续开启条件

第一次教学中的“三个指定初始模块都成功发放物品”条件已经完成，全局状态永久保持 `Completed`。

后续是否可用主要取决于：

- 是否有三个有效可用物品；
- 是否没有正在进行的 Check；
- 是否有可 Reveal 的候选模块；
- 是否满足当前 Phase 的其他条件。

`TriggeredInitialModules` 可以保留作调试/记录，但后续循环不再用它触发教学。普通 Availability 由 `SubmissionTutorialState != CollectingInitialItems`、有效物品数量和 `bCheckInProgress` 控制。

## 7.1 后续模块的处理规则

后续等待骰子显示的模块必须满足：

```text
bCountsTowardInitialUnlock = False（Class Default）
```

它们被 `RevealModuleGroup` 显示、与玩家交互并发放物品时：

- 可以调用 `TryUnlockFirstSubmissionTutorial` 或 `RefreshSubmissionAvailability` 更新物品数量；
- 不调用 `NotifyInitialModuleTriggered`；
- 不改变 `SubmissionTutorialState`；
- 不显示首次 D 教学或右上角 Attention；但当普通 Availability 为 True 时，D 键和红色图标仍然是正常可用入口。

即使未来改为真正 `SpawnActor`，新实例也因为 Class Default=False 而不具备教学资格；CoreDevice 的 Completed 状态提供最终兜底。

## 8. 防止已显示模块再次被选择

每次 Commit：

```text
SpawnedModules Add Unique(RevealedModule)
```

每次 Prepare：

```text
候选 Actor
→ NOT SpawnedModules Contains
→ 如果模块有 bAlreadyRevealed，也必须为 False
```

测试至少连续 Reveal 两个模块，确认不会重复。

## 9. 无候选模块时的 UX

如果对应阵营模块已经用完：

- `PrepareDiceCheck` 返回 False；
- 不播放旋转；
- 不清空物品；
- UI 提示例如 `NO MODULE AVAILABLE`；
- 玩家可以更换物品再次尝试，或由游戏逻辑切换 Phase。

最好在 `CanOpenSubmission` 中不要提前假定骰子阵营，因此无候选的最终检查仍放在 Prepare。

## 10. 中途取消和异常清理

如果发生 Level Transition、PlayerController EndPlay 或 Widget 被强制 Remove：

创建 CoreDevice 函数：

`CancelPendingDiceCheck`

只用于异常退出：

```text
PendingRevealModule = None
bCheckInProgress = False
不清空 SubmittedItems（让玩家下次继续）
RefreshSubmissionAvailability
```

PlayerController 同时恢复 Input Mode。

## 11. 状态变化时刷新 HUD

以下时机调用 `RefreshSubmissionAvailability`：

- 新物品加入 Inventory；
- 物品被消耗或移除；
- 第三个指定初始模块成功发放物品；
- Prepare 成功，进入 Checking；
- Commit 成功并完成清理；
- Commit 失败；
- 异常 Cancel。

HUD 通过 Dispatcher 更新入口的普通可用状态：

- `CollectingInitialItems`：隐藏 D Prompt，红色图标禁用或低亮；
- `WaitingForFirstD`：显示一次 `[D] OPEN SUBMISSION`，红色图标同时正常可点击；
- `Completed`：永远隐藏首次 D Prompt 和 Attention，只按 Availability 更新红色图标可用状态；
- `PointingToLauncher`：仅作为旧状态兼容，不再主动进入；行为应与可直接打开的状态一致。

首次通过 D 键或红色图标成功打开面板后，状态立即进入 `Completed`。后续 Inventory 变化只能刷新普通 Availability，不能重播教学。

## 12. 连续三轮测试

### 第一轮

- 收集三个初始教学物品，出现一次 `[D] OPEN SUBMISSION`。
- 分别测试用 D 键或右上角红色图标直接打开面板（每次 PIE 选择其中一种作为首次入口）。
- 确认首次成功打开后 State 立即变为 Completed。
- Reveal 模块 A。

### 第二轮

- 获取或准备三件有效物品。
- Reveal/交互新模块后确认 Tutorial State 仍为 Completed。
- 不出现 D 教学 Prompt 或红图标 Attention。
- 按 D 应直接打开；关闭后用右上角图标也应直接打开同一个面板。
- Reveal 模块 B。
- B 不能等于 A。

### 第三轮

- 再次按规则打开。
- 快速交替按 D、点击右上角图标与点击中央按钮。
- 只能创建一个 Widget、一次动画、一次 Reveal。

## 13. 常见错误

### 第二轮 D 没反应

- `bCheckInProgress` 没设回 False；
- Availability 没刷新；
- Inventory 中物品已被消耗但玩家没有新物品；
- `SubmissionPanelRef` 指向已经 Removed 的无效状态。

### 第二轮还是显示旧物品图标

- Widget 被复用但没有 Reset；
- `SubmittedItems` 没清空；
- Initialize 时没有 RefreshSlotVisuals。

### 重复 Reveal 同一模块

- Commit 没加入 `SpawnedModules`；
- Find 候选时没有过滤；
- Actor 自身 `bAlreadyRevealed` 没更新。

### 第二轮重复首次教学

- 循环清理错误重置了 `SubmissionTutorialState`；
- HUD 只看 Availability，没有 Switch Tutorial State；
- 新模块 Class Default 的 `bCountsTowardInitialUnlock` 错误为 True；
- 教学通知错误地接在 `RevealModuleGroup`；
- PlayerController 仍使用旧的本地教学 Boolean。
- `OpenSubmissionPanel` 成功路径没有设置 `Completed`；
- 仍有节点把状态设置成 `PointingToLauncher`。

## 14. 本部分验收

- [ ] Commit 后所有临时状态正确重置。
- [ ] CoreDevice 教学状态始终保留为 Completed。
- [ ] 后续 D 和右上角红色图标都直接打开同一个面板。
- [ ] 两个外部入口都不会执行 Prepare 或启动旋转。
- [ ] 只有中央 Button_Check 执行鉴定。
- [ ] 后续 Reveal、Spawn 和物品发放不会显示任何首次教学 UI。
- [ ] 旧槽位视觉不会残留。
- [ ] 已显示模块不会再次被选择。
- [ ] 连续至少三轮不产生重复 Widget 或卡死。
- [ ] 异常退出可以安全恢复。
