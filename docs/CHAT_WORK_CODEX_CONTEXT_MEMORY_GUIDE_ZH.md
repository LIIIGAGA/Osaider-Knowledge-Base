# Chat、ChatGPT Work 与 Codex：Context、会话记录与 Memory 使用指南

> 版本：v1.1  
> 整理日期：2026-08-21  
> 适用范围：ChatGPT 网页版、ChatGPT 桌面应用中的 Chat / Work / Codex，以及 Codex Local / Worktree / Cloud 运行方式。  
> 说明：产品行为可能随版本和账号设置变化。本文将 OpenAI 官方说明、当前 Windows 桌面端的实际观察和使用建议分开表述。

---

## 1. 结论先行

最重要的结论只有七条：

1. **新建对话不会自动继承上一个对话的完整 Context。**
2. **同一项目或同一文件夹主要共享文件、项目说明和当前文件状态，不等于共享其他对话的完整会话记录。**
3. **Chat 与 ChatGPT Work 使用账号或工作区提供的 ChatGPT Memory；本地 Codex 使用另一套本地 Memory。**
4. **Context、会话记录、Memory、项目文件和 Git 历史是五种不同的数据。**
5. **Local 表示任务在本机运行，不等于所有内容都只存本机；Cloud 表示任务在远程环境运行，也不等于它能直接读取本机文件。**
6. **Git/GitHub 只能备份被 Git 跟踪的项目文件，不能自动备份 Chat、Work 或 Codex 的会话记录与 Memory。**
7. **读取本机环境与把会话保存到云端在技术上并不冲突；但当前官方文档没有保证 Local 的完整原始会话会自动同步为账号云端副本。**

一句话概括三种模式：

- **Chat**：适合快速问答、解释、讨论、头脑风暴和短内容。
- **Work**：适合把多个来源和工具组合起来，完成可审核、可复用的交付物。
- **Codex**：适合直接在项目文件夹或 Git 仓库中修改文件、运行命令、测试和管理版本。

## 2. 总体对比

| 项目 | Chat | ChatGPT Work | Codex |
|---|---|---|---|
| 主要目标 | 回答问题、讨论、解释、短草稿 | 完成较大的多步骤任务或交付物 | 修改项目、代码、文档和 Git 仓库 |
| 典型输出 | 回答、建议、短文本 | 文档、演示、表格、调研、工作流 | 文件修改、代码、测试结果、Git 提交 |
| 是否自动继承上一对话全文 | 否 | 否 | 否 |
| 跨对话连贯性 | 通常较强，可能使用账号 Memory | 可能使用账号/工作区 Memory | 本地运行时使用独立的本地 Codex Memory；默认关闭 |
| 同一项目中新对话可共享什么 | 项目文件、项目说明、连接来源 | 项目文件、项目说明、连接来源 | 同一工作树中的文件、Git 状态、`AGENTS.md` 和项目配置 |
| 是否自动读取同项目其他对话全文 | 否 | 否 | 否 |
| 本地文件访问 | 普通 ChatGPT 项目不能直接访问本机文件；需上传、连接或使用桌面端可用工具 | Work Local 可使用获准的本机文件、应用和浏览器 | Local/Worktree 可直接在获准项目目录工作 |
| 长期规则的最佳载体 | 自定义指令、项目说明 | 项目说明、共享来源、正式文档 | `AGENTS.md`、项目文档、规则、Skills |
| 最适合 | 快速交流与思考 | 综合办公和可交付成果 | 项目实施、代码、文档、测试、Git |

## 3. 五个容易混淆的概念

### 3.1 Context（当前上下文）

Context 是模型在**当前这一次回答**时能够使用的信息集合，可能包括：

- 当前对话中的消息；
- 当前附加或选中的文件；
- 项目说明、项目来源和连接的数据；
- 当前打开的文件或选中的代码；
- 系统提供的规则和权限；
- 被系统选中并注入的相关 Memory；
- 工具刚刚读取或检索到的结果。

Context 不是永久存档。它有容量限制，长对话可能被压缩或只保留更相关的信息。

### 3.2 会话记录（Transcript / Chat History）

会话记录是某一个具体对话中你和 Agent 的消息、工具操作和结果记录。

- 继续原对话时，可以延续这份记录。
- 新建对话时，不会自动复制整份旧记录。
- 即使两个对话位于同一项目或同一文件夹，它们仍是两份独立记录。

### 3.3 Memory（跨对话记忆）

Memory 是从过去工作中提取的、可能对未来有帮助的少量长期信息。它不是完整聊天记录，也不是可靠的逐字档案。

Memory 适合保存：

- 稳定的个人偏好；
- 常用工作方式；
- 长期项目背景；
- 有持续价值的事实或决定。

Memory 不适合作为唯一载体保存：

- 必须严格执行的项目规则；
- 精确的技术参数；
- 完整任务进度；
- 重要交付要求；
- 密码、密钥和其他秘密。

### 3.4 项目上下文（Project Context）

项目上下文指项目中的共享资料，例如：

- 项目说明；
- 上传文件；
- 连接的数据源；
- 本地项目连接的文件夹；
- Codex 自动发现的 `AGENTS.md`、Skills 和项目配置。

项目上下文是 Context 的一个来源，但不等于当前 Context，也不等于 Memory。

### 3.5 项目文件与 Git 历史

项目文件是实际存在于项目目录中的内容。Git 历史是这些文件的版本记录。

它们通常是跨对话传递重要信息最可靠的方式，因为新对话可以重新读取文件，Git 还可以保存版本并推送到远程仓库。

## 4. Chat 模式

### 4.1 新对话是否继承上一对话

不会继承上一对话的完整消息记录。

如果你感觉 Chat 跨对话非常连贯，通常是以下因素造成的：

- ChatGPT Memory 提供了与你相关的长期信息；
- 系统从过去工作中提取了相关信息；
- 两个对话位于同一个 ChatGPT 项目，因而共享项目说明、文件和来源；
- 自定义指令持续生效。

因此，Chat 的体验更像“记得与你有关的重点”，而不是“完整看过所有旧对话”。

### 4.2 会话记录保存

Chat 的会话历史主要与 ChatGPT 账号同步，因此通常可以在网页或其他已登录设备上看到。桌面应用可能存在本地缓存，但不应把某个本地缓存路径当作 Chat 历史的唯一正式副本。

OpenAI 官方文档没有为普通 Chat 历史提供一个类似 `CODEX_HOME` 的、由用户直接管理的本地权威路径。

### 4.3 Memory

Chat 使用 ChatGPT 的账号级 Memory，由“设置 → 个性化”管理。Memory 是否可用以及具体行为可能取决于账号、套餐、地区和工作区策略。

### 4.4 适用场景

- 快速问答；
- 概念解释；
- 头脑风暴；
- 文案润色；
- 短草稿；
- 在采取行动前讨论方案。

## 5. ChatGPT Work 模式

### 5.1 Work 与 Chat 的核心区别

Work 不是另一种“聊天记忆”，而是一种面向交付结果的工作方式。

适合 Work 的任务通常：

- 包含多个步骤；
- 使用多个文件、来源、插件或工具；
- 需要较长时间；
- 最终要生成可审核、编辑或复用的成果；
- 需要定期重复、监控或更新。

### 5.2 Work 新对话的 Context

Work 新对话不会自动读取同一项目中其他 Work 对话的完整记录。

同一 ChatGPT 项目中的 Chat 和 Work 可以共享：

- 上传文件；
- 项目说明；
- 连接来源；
- 与账号/工作区设置相符的 Memory。

但每个对话仍有自己的会话记录。

### 5.3 Work 的 Memory

Work 使用账号或工作区允许的 ChatGPT Memory，不使用本地 Codex 的 `memories` 文件夹和本地 Memory 控制。

“工作区 Memory”主要是组织管理员对 Memory 功能的策略和权限控制，**不是所有成员和 Agent 自动共享的一池记忆**。团队需要共享的正式知识，应放入共享项目、知识库、项目说明或正式文档。

### 5.4 Work Local

Work Local 适合任务需要：

- 读取或修改本机文件；
- 使用本机应用；
- 操作当前浏览器；
- 直接处理尚未上传的本地资料。

“本地运行”说明任务执行依赖当前电脑，并不自动证明所有对话数据都只保存在本地。

在本机当前桌面端环境中，我们曾实际观察到 Work/Codex 的本地运行恢复记录出现在：

```text
D:\ChatGPT-Codex\sessions\年\月\日\rollout-*.jsonl
```

这是因为当前用户已经把 `CODEX_HOME` 从默认 C 盘迁移到：

```text
D:\ChatGPT-Codex
```

这条路径属于**当前机器和当前版本的实际观察**。不能据此推断所有 Work Local 对话一定有完整云端副本；误删本地恢复记录后，不应假定账号云端必然能够恢复。

### 5.5 Work Cloud

Work Cloud 适合：

- 关闭桌面应用或电脑后仍需继续运行；
- 希望从网页或移动设备继续任务；
- 定期执行网页研究、检查或更新；
- 任务不依赖未上传的本机文件或本机应用。

Cloud 默认不能随意读取你的本机文件。需要将内容放入远程项目、上传文件、连接数据源，或通过获准工具提供给它。

## 6. Codex 模式

### 6.1 Codex 的核心定位

Codex 面向项目目录、代码库和 Git 工作流，擅长：

- 查找、读取和修改项目文件；
- 编写或重构代码；
- 运行命令、测试和构建；
- 检查 Git 状态和差异；
- 提交、推送分支和创建 Pull Request；
- 根据 `AGENTS.md`、项目配置和 Skills 执行长期规则。

Codex 也可以完成非编程文件任务，但 Work 的交互方式更偏向一般知识工作和最终交付物。

### 6.2 同一项目文件夹中的新对话

在同一项目文件夹中新建 Codex 对话时：

会共享或重新读取：

- 当前项目文件；
- 前一个对话已经写入文件的修改；
- 当前 Git 状态和提交历史；
- 主项目目录下的 `AGENTS.md`；
- 可发现的 `.codex/config.toml`、Skills 和规则。

不会自动共享：

- 其他 Codex 对话的完整文字记录；
- 只在旧对话中讨论、但从未写进文件的决定；
- 旧对话中尚未形成文件的临时推理过程。

官方文档的原则是：同一项目中的对话可以处理同一批文件，但每个对话保留自己的 transcript。

### 6.3 能否要求 Codex 读取旧对话

可以尝试，但需要满足以下条件：

- 旧任务仍然存在且没有损坏；
- 当前应用提供读取旧任务的能力；
- 当前 Agent 拥有相应权限；
- 你最好给出准确的旧任务标题、链接或其他识别信息。

建议提示词：

```text
请读取同一项目中名为“旧任务标题”的任务，提取：
1. 已完成事项；
2. 关键决定；
3. 修改过的文件；
4. 未完成事项；
5. 当前任务继续工作前必须知道的限制。
```

但最可靠的方式仍然是：

- 需要完整延续时，直接继续原任务；
- 需要新开任务时，让旧任务先生成交接摘要；
- 把长期状态写入 `docs/PROJECT_STATUS.md`；
- 把必须遵守的规则写入 `AGENTS.md`。

### 6.4 Codex Local

Local 表示 Codex 直接在当前项目目录工作。它能够看到当前工作树中的真实文件，修改也直接出现在该目录中。

适合：

- 处理本机尚未推送的项目；
- 使用本机安装的软件和依赖；
- 直接运行 Unreal、Node、Python 或其他项目工具；
- 在当前 Git 分支上立即修改。

### 6.5 Codex Worktree

Worktree 也在本机运行，但它使用独立的 Git 工作树隔离文件修改。

适合：

- 同时开展多个互不干扰的任务；
- 不希望 Agent 直接修改主工作目录；
- 需要独立分支、独立测试或独立审查。

Worktree 隔离的是**项目文件和 Git 修改**，不是自动创建一套新的账号 Memory。

### 6.6 Codex Cloud

Cloud 表示 Codex 在配置好的远程环境中运行。

适合：

- 任务需要远程持续执行；
- 项目已经位于远程 Git 仓库；
- 希望使用隔离的远程环境；
- 不希望依赖当前电脑保持开机。

Codex Cloud 通常围绕远程 Git 仓库或上传/连接的资源工作。它不能因为你本机存在某个文件夹，就自动读取该文件夹中未上传的内容。

不要假定 Codex Cloud 会直接使用本机 `D:\ChatGPT-Codex\memories` 中的 Memory；官方明确区分了 ChatGPT Memory 与本地 Codex Memory。

## 7. 本地 Codex 的会话与 Memory 保存路径

### 7.1 默认路径

OpenAI 官方文档说明，本地 Codex 状态保存在 `CODEX_HOME` 下，默认是：

```text
~/.codex
```

Windows 默认通常对应：

```text
C:\Users\用户名\.codex
```

### 7.2 当前机器的路径

当前用户已设置：

```text
CODEX_HOME=D:\ChatGPT-Codex
```

因此新建的本地 Codex 会话、配置和未来生成的本地 Memory 应以该目录为基础。已经在迁移前创建的旧会话可能仍记录原 C 盘路径，迁移不会自动修复已经丢失的旧文件。

### 7.3 常见内容

当前环境可能出现：

```text
D:\ChatGPT-Codex\config.toml
D:\ChatGPT-Codex\sessions\...
D:\ChatGPT-Codex\memories\...
D:\ChatGPT-Codex\history.jsonl
```

不同客户端版本可能使用不同的具体文件组织方式。例如桌面端可能使用按日期分类的 `sessions/.../rollout-*.jsonl`，而官方文档也使用 `history.jsonl` 作为历史持久化示例。

### 7.4 本地 Codex Memory

本地 Codex Memory：

- 默认关闭；
- 开启后，Codex 可以从符合条件的旧对话中提取有用信息；
- 活跃或过短的会话可能被跳过；
- 生成不是即时发生，通常会等待会话闲置；
- 可能因额度阈值或设置而跳过；
- 主要文件位于 `CODEX_HOME\memories`；
- 可通过 `/memories` 控制当前对话是否使用旧 Memory，以及是否参与未来 Memory 生成。

当前机器此前检查时尚未发现：

```text
D:\ChatGPT-Codex\memories
```

因此当时本地 Codex Memory 很可能尚未开启或尚未生成。这也是新 Codex 对话跨任务连贯性弱于 Chat 的一个重要原因。

## 8. 新对话到底会自动获得什么

| 新对话类型 | 自动获得 | 不会自动获得 |
|---|---|---|
| 普通 Chat | 当前提示、自定义指令、可能相关的账号 Memory | 上一个对话的完整消息记录 |
| 同一 ChatGPT 项目中的 Chat | 上述内容 + 项目文件、说明、连接来源 | 同项目所有聊天的完整全文 |
| 同一项目中的 Work | 项目文件、说明、来源、账号/工作区允许的 Memory | 其他 Work 对话完整记录 |
| 同一文件夹中的 Codex | 当前文件、Git 状态、项目规则、可能的本地 Codex Memory | 其他 Codex 对话完整记录 |
| Codex Worktree | 独立工作树、对应分支、项目规则 | 主工作树中未同步的临时修改、其他对话全文 |
| Work/Codex Cloud | 远程环境中可用的仓库、上传文件和连接来源 | 本机未上传文件、本地 Codex Memory 文件 |

## 9. Local、Cloud 与 Worktree 的区别

| 运行方式 | 在哪里运行 | 能否直接使用本机文件 | 电脑关机后能否继续 | 文件隔离方式 |
|---|---|---|---|---|
| Local | 当前电脑 | 可以，在授权范围内 | 通常不能 | 直接使用当前项目目录 |
| Worktree | 当前电脑 | 可以，在授权范围内 | 通常不能 | 独立 Git 工作树和分支 |
| Cloud | 远程环境 | 不能直接读取未上传的本机文件 | 可以 | 远程环境/远程仓库 |

“Local / Cloud / Worktree”描述的是**任务在哪里运行以及文件如何隔离**；“Chat / Work / Codex”描述的是**工作方式和 Agent 能力重点**。这两组概念不要混在一起。

### 9.1 为什么读取本机环境时，会话不一定完整保存在云端

首先要区分三种不同的“云端”：

| 概念 | 实际含义 |
|---|---|
| 云端运行 | Agent 在远程容器中执行任务，而不是直接在你的电脑上运行 |
| 账号会话同步 | 对话可以通过同一账号在网页、桌面端或其他设备中查看和继续 |
| 云盘备份 | OneDrive、Dropbox 或其他备份工具复制本地会话文件 |

这三件事可以组合，但不是同一个功能。Local 只是在说明任务在哪里运行、能够使用哪些文件，并不必然决定会话是否同步；Cloud 也不代表它能够直接读取本机磁盘。

从技术上说，产品完全可以让 Agent 在本机读取文件，同时把用户消息和助手回复同步到账号云端。许多软件都采用这种模式。因此，问题不是“技术上不能”，而是当前 Codex / Work 没有在官方文档中把 **Local 完整原始会话自动云同步和云端恢复**列为一项明确保证。

本地 Agent 的记录也不只是普通聊天文字，还可能包括：

- 本机绝对路径、命令和终端输出；
- 工具调用结果、代码差异和测试日志；
- 文件内容片段、权限状态和错误恢复信息；
- 可能被误输出的密钥、令牌或其他敏感数据；
- 数量较大、仅对当前电脑环境有意义的执行日志。

因此，完整上传这些原始记录会涉及隐私、企业数据策略、存储容量和同步冲突。即使云端保留了聊天文字，如果没有当时的本地文件版本、应用状态和权限，也不一定能够真正重现或继续原任务。这些属于根据 Local 和 Cloud 运行结构作出的产品设计解释，并不是 OpenAI 官方公布的完整设计理由。

一种更理想、也更容易兼顾隐私与连续性的设计是：

- 用户消息和助手回复可以选择同步到账号云端；
- 本地工具日志和敏感执行细节默认只保存在本机；
- 用户可以选择是否上传附件、项目快照或完整执行轨迹；
- 云端清楚标记哪些本地环境状态无法恢复。

但在官方明确提供这种设置和恢复保证之前，不应把账号侧看到的任务条目当作 `CODEX_HOME\sessions` 的完整云端备份。

## 10. 项目、文件夹、工作区与远程 Git 仓库

### 10.1 ChatGPT 项目

用于组织相关聊天、上传文件、项目说明和连接来源。一个项目中可以同时包含 Chat 和 Work 对话。

### 10.2 本地项目文件夹

是电脑上的真实目录。Work Local 或 Codex Local 获得权限后可以读取和修改其中的文件。

### 10.3 工作区（Workspace）

通常表示账号所属的组织环境、权限和管理员策略。工作区 Memory 设置主要决定成员能否使用 Memory，而不是让所有人的 Agent 自动共享私人记忆。

### 10.4 Git 仓库

是带有 Git 版本历史的项目目录。Git 仓库可以只存在本地，也可以连接到远程服务。

### 10.5 远程 Git 仓库

远程仓库不只指 GitHub，也可以位于 GitLab、Bitbucket、自建 Git 服务等平台。当前 Osaider 知识库连接的是 GitHub：

```text
https://github.com/LIIIGAGA/Osaider-Knowledge-Base.git
```

## 11. Git 能备份什么，不能备份什么

Git/GitHub 可以备份：

- 被 Git 跟踪的 Markdown 文档；
- 项目图片、脚本和配置；
- `AGENTS.md`；
- `docs/PROJECT_STATUS.md`；
- 每次提交的文件版本。

Git/GitHub 默认不能备份：

- ChatGPT 普通 Chat 的账号会话历史；
- `D:\ChatGPT-Codex\sessions` 中的 Codex/Work 本地会话文件；
- `D:\ChatGPT-Codex\memories` 中的本地 Codex Memory；
- 被 `.gitignore` 排除的缓存和本地工具；
- 未提交、未推送的修改。

不要把整个 `CODEX_HOME` 直接提交到项目 Git 仓库，因为其中可能包含身份验证信息、日志、本机配置和不适合公开的数据。

## 12. 针对当前用户的推荐工作方式

### 12.1 Chat

用于：

- 快速询问概念；
- 讨论设计思路；
- 比较方案；
- 获得解释和建议。

### 12.2 Work

用于：

- 调研并整合多个来源；
- 制作 Word、PDF、PPT、表格和完整报告；
- 执行多步骤的综合知识工作；
- 需要最终可审核成果的任务。

选择 Work Local：任务依赖本机文件或应用。  
选择 Work Cloud：任务需要远程持续运行，且所需文件已经上传或可通过连接来源获得。

### 12.3 Codex

用于：

- 修改 Osaider 知识库；
- 更新 Markdown 文档；
- 检查项目目录；
- 管理 Git 状态；
- 提交并推送 GitHub；
- 修改 Unreal 项目配套脚本或代码；
- 运行测试、构建和自动化工具。

### 12.4 跨对话持续工作的最佳实践

建议在每个长期项目中维护：

```text
AGENTS.md
docs/PROJECT_STATUS.md
docs/DECISIONS.md
```

用途：

- `AGENTS.md`：必须始终遵守的规则和工作方式；
- `PROJECT_STATUS.md`：已完成、正在进行、下一步和阻塞项；
- `DECISIONS.md`：重要决定、原因、日期和影响。

结束重要对话前，可以要求 Agent：

```text
请把本次工作的完成项、关键决定、修改文件、风险和下一步更新到
docs/PROJECT_STATUS.md；把需要未来所有 Agent 遵守的规则更新到 AGENTS.md。
```

这样，即使新对话没有读取旧会话全文，也可以通过项目文件恢复可靠上下文。

## 13. 会话数据的备份建议

当前 `CODEX_HOME` 已经迁移到 D 盘，这是减少 C 盘占用的正确方向。还应增加独立备份：

### 建议备份

```text
D:\ChatGPT-Codex\sessions
D:\ChatGPT-Codex\memories
D:\ChatGPT-Codex\config.toml
```

### 谨慎处理

```text
D:\ChatGPT-Codex\auth.json
```

`auth.json` 可能包含身份验证相关信息，不应上传到 GitHub、公共网盘或项目仓库。

### 推荐方案

- 使用 Windows 文件历史记录或可信的加密备份工具；
- 定期把 `sessions` 和 `memories` 备份到另一个磁盘；
- 如果需要异地容灾，可将这两个目录备份到启用了版本历史的私人云盘，但应先确认其中没有不适合上传的项目内容；
- 不要把整个 `CODEX_HOME` 直接同步到公开 GitHub；
- 不要使用清理工具自动删除整个 `D:\ChatGPT-Codex`；
- 项目成果继续通过 Git 提交并推送 GitHub；
- 重要结论同步写入项目文档，不只保存在会话里。

## 14. 常见误区速查

| 误区 | 正确理解 |
|---|---|
| Chat 新对话会完整读取所有旧对话 | 不会；它可能使用相关 Memory，但不是旧对话全文 |
| 同一文件夹中的所有对话共享 Context | 共享文件状态，不共享完整对话记录 |
| 项目上下文就是 Context | 项目上下文只是当前 Context 的一个来源 |
| Memory 就是聊天记录 | Memory 是提取后的少量长期信息，不是完整记录 |
| 工作区 Memory 是团队共享记忆池 | 主要是工作区对 Memory 功能的权限和策略控制 |
| Local 表示云端完全没有任何数据 | Local 说明任务在本机运行；数据同步和保存要分别判断 |
| 能读取本机文件就不能同步云端会话 | 技术上可以同时实现，但当前不应假定 Local 原始会话有完整、可恢复的账号云端副本 |
| 侧边栏能看到任务就证明会话已完整云备份 | 任务索引、聊天显示和本地原始会话恢复文件可能不是同一份数据 |
| Cloud 可以直接读取 C/D/E 盘 | 不能，除非上传、连接或通过获准工具提供 |
| Worktree 是云端副本 | 不是；Worktree 通常是在本机创建的独立 Git 工作树 |
| 改变项目默认位置会改变会话保存位置 | 项目路径和 `CODEX_HOME` 是两套路径 |
| 推送 GitHub 会备份会话 | 不会；只备份被 Git 跟踪并提交、推送的项目文件 |
| 开启 Memory 后可以不写项目文档 | 不建议；必须可靠执行的内容应写入项目文件 |

## 15. 最终选择指南

如果只是想问一个问题、讨论想法或获得简短文字：**使用 Chat**。

如果希望 Agent 使用多个资料和工具完成一份正式成果：**使用 Work**。

如果希望 Agent 直接操作项目文件、代码、测试或 Git：**使用 Codex**。

如果任务依赖本机文件或应用：**选择 Local**。

如果任务需要在电脑关闭后继续，且资料已上传或位于远程来源：**选择 Cloud**。

如果希望并行修改代码且不干扰主项目目录：**选择 Worktree**。

如果希望新对话准确理解旧工作的决定和进度：**不要只依赖 Memory，把信息写入 `AGENTS.md`、`PROJECT_STATUS.md` 和 Git 提交。**
